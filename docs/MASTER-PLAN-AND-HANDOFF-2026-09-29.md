# Agentnexos — الخطة الرئيسية والتسليم الكامل

**التاريخ:** 2026-09-29

**الحالة:** المرجع الحاكم للمشروع

**المستودع:** `adham-younes/agentnexos`

**الإنتاج:** `https://compute-the-platform-to-build-six-fawn.vercel.app/`

هذه الوثيقة تلغي أي تعريف قديم يحصر Agentnexos في «معالجة المستندات». الوثائق السابقة تظل سجلًا تاريخيًا، لكنها لا تقود التطوير عند التعارض.

## 1. الرؤية

Agentnexos منصة لبناء وتشغيل أنظمة وكلاء مخصصة للمؤسسات والشركات في مصر والخليج والشرق الأوسط. تبدأ من مشكلة تشغيل حقيقية، تفهم بيانات المؤسسة وأنظمتها وحدود السلطة، ثم تبني سير عمل وكيلًا ينفذ أو يقترح أو يصعّد، مع موافقات بشرية وسجل تدقيق ودليل نتيجة.

- تحويل عملية مؤسسية واضحة إلى عقد تنفيذ قابل للقياس، لا عرض تقني عام.
- ربط المعرفة والأدوات الحالية بدل فرض استبدال أنظمة المؤسسة.
- تشغيل عربي/إنجليزي مع حساسية للبيانات والسيادة والحوكمة الإقليمية.
- فصل القرار الاحتمالي للنموذج عن الحالة الحتمية لسير العمل.
- منح الوكيل أقل صلاحية لازمة، وإثبات ما فعله وما نتج عنه.

ليست المنصة Chatbot عامًا، ولا متجر Prompts، ولا واجهة توهم بوجود تكاملات غير مبنية.

## 2. حصيلة البحث والدراسات

تمت مراجعة مادتي المالك `AI AGENT STRATGEY.rtf` و`agentic-ai-mena-strategy-2026-09-19.md` باعتبارهما مصادر بحثية، لا تعليمات تنفيذ تلقائية. الخلاصة المعتمدة:

1. **عقد التنفيذ أولًا:** الهدف، المدخلات، مصدر الحقيقة، الحالات، أدوات القراءة/الكتابة، حدود الصلاحية، الموافقات، معيار النجاح، ودليل النتيجة.
2. **محرك سير العمل يملك الحالة:** النموذج يقترح ويصنف ويحلل غير المنظم؛ النظام الحتمي يملك الانتقالات، المهلات، إعادة المحاولة، والتعافي.
3. **Control Plane وData Plane منفصلان:** إدارة التعريفات والسياسات عن تنفيذ الأدوات والبيانات الحساسة.
4. **تدرج الصلاحيات:** قراءة، اقتراح، تنفيذ بعد موافقة، ثم تنفيذ مستقل فقط بعد قياس واعتماد.
5. **Replay Lab:** كل تشغيل قابل لإعادة العرض والتقييم دون تكرار أثر خارجي.
6. **Evidence Log:** النتيجة تثبت من النظام النهائي أو Artifact أو حالة API موثقة، لا من رسالة النموذج.
7. **التعلم من المراجعة البشرية:** التصحيحات تتحول إلى حالات تقييم، لا ذاكرة غير مضبوطة.
8. **المنطقة ميزة منتج:** العربية وRTL وسيادة البيانات وقنوات العمل المحلية ليست ترجمة سطحية.

التحليل التحريري السابق لعشر منصات موجهة للعربية أو MENA يُستخدم لفهم أنماط الرسائل والفجوات فقط، وليس تصنيفًا مطلقًا ولا مصدرًا لنسخ النصوص: Mozn، Arabic.AI، SandRock، Gaia، tkana، Oryx Data/OCT.AI، Alpha Pro MENA، Elama، Menatic، Conneqt. أي تحديث تنافسي لاحق يعتمد على المواقع الرسمية وتاريخ وصول واضح.

## 4. المعمارية المستهدفة

### 4.1 الطبقات

1. واجهة ثنائية اللغة في Next.js على `/[locale]/agentnexos`.
2. Vercel AI SDK للتدفق ورسائل الواجهة وأجزاء الأدوات.
3. Mastra للوكلاء وWorkflows والذاكرة والتقييم بعد التحقق من الإصدار المثبت.
4. منسق TypeScript حتمي يقرر متى يُستدعى كل وكيل.
5. أدوات بعقود Zod، timeouts، retries محدودة، idempotency، وتصنيف قراءة/كتابة/خطر.
6. Supabase للحالة الدائمة والمؤسسات والموافقات والتدقيق والذاكرة والتقييم مع RLS.
7. Observability تربط `thread_id`, `run_id`, `step_id`, `tool_call_id` بدليل النتيجة.

### 4.2 فريق الوكلاء

| الدور | النموذج | مفتاح البيئة | المسؤولية |
|---|---|---|---|
| محلل العملية | `qwen/qwen3.8-27b` | `GROQ_API_KEY` | فهم الطلب وبناء عقد التنفيذ والأسئلة الناقصة |
| مخطط/منفذ الأدوات | `qwen/qwen3.8-27b` | `GROQ_API_KEY1` | تحويل العقد إلى خطوات وأدوات مقيدة |
| المراجع والمشرف | `openai/gpt-oss-120b` | `GROQ_API_KEY2` | نقد الخطة والتحقق من النتيجة والمخاطر |

هذه أسماء مفاتيح فقط؛ لا تُحفظ القيم. توزيع المفاتيح ليس حدًا أمنيًا ولا مبررًا لتشغيل الثلاثة على كل رسالة. يبدأ المنسق بوكيل واحد ويصعّد عند الحاجة، بحد توازٍ ابتدائي 2 وrate limiting وbackoff وcircuit breaker.

وفق توثيق Groq بتاريخ الوثيقة، `qwen/qwen3.8-27b` نموذج Preview بحد إكمال 16,384 token، و`openai/gpt-oss-120b` نموذج Production بحد 65,536 token. تُضبط القيم كسقف تقني لا كهدف استهلاك؛ الافتراضي أصغر ويرتفع للمهمة الصعبة فقط. لأن Qwen Preview، يجب توفير fallback واختبار دوري.

المراجع: [Groq Models](https://console.groq.com/docs/models)، [API Reference](https://console.groq.com/docs/api-reference)، [Rate Limits](https://console.groq.com/docs/rate-limits)، [Remote MCP](https://console.groq.com/docs/tool-use/remote-mcp)، [Structured Outputs](https://console.groq.com/docs/structured-outputs).

### 4.3 دورة التشغيل

`طلب → فحص صلاحية وسياق → عقد تنفيذ → خطة → تصنيف مخاطر → موافقة إن لزم → أداة → تحقق من النظام النهائي → تسجيل الدليل → رد`

- لا يبقى stream مفتوحًا انتظارًا للموافقة؛ تُحفظ الحالة ويستأنف طلب موثق جديد.
- كل أداة كتابة لها `idempotency_key` وموافقة بمعلمات ثابتة تنتهي صلاحيتها.
- الفشل الجزئي يعالج بـreconciliation أو Saga/compensation، لا بإعادة أعمى.
- Structured Output لا يغني عن Zod؛ وإذا تعارض streaming مع tools تُقسم العملية إلى خطوات.

### 4.4 الأدوات

- بحث لحظي بمصادر وتواريخ وروابط.
- جلب URL مع allowlist وحماية SSRF وحدود حجم ووقت.
- تحليل ملفات آمن يراعي حدود رفع Serverless.
- تنفيذ كود داخل Sandbox معزول، لا shell على خادم المنتج.
- GitHub قراءة أولًا، ثم كتابة بموافقة ونطاق repository محدد.
- Supabase بأدوار منفصلة وsecret في الخادم فقط.
- Vercel للقراءة/التحقق أولًا والنشر عبر CI.
- البريد/CRM/ERP لاحقًا لحالة استخدام مثبتة، لا كشعارات.

### 4.5 قاعدة البيانات

الجداول الأساسية: `organizations`, `profiles`, `memberships`, `agent_threads`, `agent_messages`, `agent_runs`, `agent_steps`, `tool_calls`, `approvals`, `artifacts`, `memories`, `integration_connections`, `audit_events`, `eval_cases`, `eval_runs`.

- `organization_id` وRLS على كل بيانات العميل.
- لا أسرار في الجداول العامة؛ secret manager مع reference فقط.
- append-only للأحداث والتدقيق وسياسة retention معلنة.
- فصل working state عن episodic memory والمعرفة المؤسسية.
- فلترة صلاحيات الاسترجاع قبل إرسال السياق للنموذج.
- migrations في Git، ثم بيئة تطوير واختبار فصل مؤسستين قبل الإنتاج.

## 5. المراحل حتى الإنتاج النهائي

### المرحلة 3 — التوثيق والهوية والغلاف الآمن

- اعتماد هذه الحزمة وإزالة تضارب التعريفات.
- تصميم 2–3 اتجاهات لأيقونة Agentnexos ثم يختار المالك اتجاهًا واحدًا؛ لا استبدال قبل الاختيار.
- إنشاء shell لمسار الوكيل خلف feature flag دون محادثة وهمية.
- إصلاح ESLint وإضافة CI للـtypecheck وi18n وbuild.

**البوابة:** وثائق مترابطة، اختيار أيقونة، اختبارات وvisual QA، ثم Preview وProduction موثق.

### المرحلة 4 — Supabase والهوية والحالة

- مشروع/بيئات Supabase، migrations، Auth، المؤسسات والعضويات وRLS.
- جداول التشغيل والموافقة والتدقيق والـartifacts.
- اختبار أن مؤسسة A لا ترى مؤسسة B.

**البوابة:** RLS وtenant isolation وSecurity/Performance advisors وrollback migration، ثم Production.

### المرحلة 5 — Runtime متعدد الوكلاء

- تثبيت AI SDK وMastra بعد قراءة توثيق الإصدار الفعلي.
- Groq والنماذج الثلاثة والتوجيه والميزانيات والمهلات وfallback.
- Chat ثنائي اللغة مع streaming وحالات الأدوات والأخطاء.
- أداة قراءة واحدة حقيقية وإجابة تستشهد بالدليل.

**البوابة:** golden evals، اختبارات غياب مفتاح/نموذج وإلغاء stream وtrace، ثم Production خلف flag.

### المرحلة 6 — الأدوات والموافقات والذاكرة

- بحث حي وfetch آمن وartifacts وSandbox وأول تكامل مؤسسي محدد.
- approval gate دائم وidempotency وexpiration وreconciliation.
- working/episodic/semantic memory بسياسات retention وحذف.

**البوابة:** رحلة تقرأ ثم تطلب موافقة ثم تكتب ثم تتحقق، مع replay بلا تكرار أثر، ثم Production.

### المرحلة 7 — التقييم والأمان والمراقبة

- تقييمات عربية/إنجليزية للنجاح والفشل والهجوم.
- قياس جودة الخطة واختيار الأداة والنتيجة وlatency وtoken/cost وتدخل الإنسان.
- prompt injection defenses وegress policy وredaction وrate limits.
- dashboards وتنبيهات وrunbooks وbackup/restore.

**البوابة:** thresholds واختبارات red-team وrestore/incident drills، ثم Production.

### المرحلة 8 — المحتوى والصفحات الكاملة

- Platform وSolutions وIndustries وSecurity وResources وAbout/Contact وPrivacy/Terms باللغتين.
- كل حالة استخدام تربط مشكلة بعقد تنفيذ ونتيجة ودليل دون ادعاء غير حقيقي.
- SEO وsitemap وOG وaccessibility وperformance budgets.

**البوابة:** لا روابط ميتة أو placeholders، مراجعة قانونية، visual QA وLighthouse/axe، ثم Production.

### المرحلة 9 — Beta مؤسسي

- onboarding مؤسسة تجريبية وconnector حقيقي وsupport وflags وquotas.
- قياس عملية كاملة وتحويل المراجعات إلى eval cases.

**البوابة:** تشغيل واقعي مراقب، لا P0/P1 مفتوح، rollback مجرب، ثم Production محدود.

### المرحلة 10 — الإطلاق العام

- domain وهوية نهائية وSLA/SLO ودعم وتسعير معتمد.
- تدقيق أمان وخصوصية ومطالبات تسويقية وcapacity/cost model.

**البوابة:** موافقة المالك، نجاح الرحلات الحية، نشر `main`، إثبات SHA والصحة، وسجل إصدار نهائي.

## 6. بروتوكول كل مرحلة

1. اكتب النطاق والملفات ومعيار النجاح قبل التعديل.
2. التقط baseline للصفحات المتأثرة.
3. نفذ أصغر تغيير يحقق الهدف.
4. شغّل typecheck وi18n وbuild واختبارات المرحلة.
5. افحص 390/768/1440 بالعربية والإنجليزية والرحلة المتأثرة.
6. أنشئ Preview وسجل الرابط والـSHA.
7. ادمج إلى `main` بعد البوابات فقط.
8. انتظر Vercel Production `READY` واختبر الرابط الفعلي.
9. أضف سجل إصدار يشمل التراجع والمشكلات غير القاتلة.

## 7. تعريف الإنجاز النهائي

لا تعتبر Agentnexos مكتملة إلا عندما يستطيع مستخدم موثق اختيار مؤسسة، بدء محادثة، تحويل طلب إلى عقد تنفيذ، تشغيل أداة حقيقية ضمن صلاحية، إيقاف الكتابة لحين الموافقة، استئناف التشغيل من قاعدة البيانات، التحقق من النتيجة، ومراجعة trace/audit باللغتين؛ مع فشل آمن عند غياب مفتاح أو نموذج أو تكامل.

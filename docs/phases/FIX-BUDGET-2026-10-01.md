# تصحيح سقف التطبيق وربطه بإعداد فعلي — 1 أكتوبر 2026

## السبب

السقف 5/24h كان قيد تجربة داخل RPC وفي نسخة الواجهة، لا حد Groq ولا Supabase ولا خطة اشتراك المستخدم. الإصلاح السابق أزال انتظار 30 ثانية وفسر 429 لكنه أبقى هذا السقف الصغير؛ لذلك لم يعالج اعتراض المالك على الاستخدام المدفوع. هذا الإصدار يصحح السياسة نفسها.

اختبار مفتاح Groq الذي قدمه المالك، بطلبي استكمال صغيرين ناجحين 200، أظهر للنموذجين openai/gpt-oss-120b و qwen/qwen3.8-27b: x-ratelimit-limit-requests:500000 (RPD)، x-ratelimit-limit-tokens:250000 (TPM). الهيدر لا يثبت RPM؛ [صفحة حدود المنظمة](https://console.groq.com/settings/limits) هي مرجعه. [الوثائق](https://console.groq.com/docs/rate-limits) تؤكد وحدات الهيدر وأن مفاتيح المنظمة تشترك في حدودها. لم يُحفظ المفتاح في الملفات أو Git ولم يُستبدل في Vercel؛ طُلب تدويره بعد مشاركته في المحادثة. لا توكنات/طلبات اختبار ضغط لإثبات حدود أعلى.

## التنفيذ

- جدول إعداد singleton `agentnexos_demo_limits`:1000 طلب لكل اتصال/24h و 10000 إجمالًا/24h. هذه ميزانية التطبيق المستقل الذي يخدم واجهة عامة، لا انعكاس 500000 لكل زائر أو ادعاء بحد RPM جديد. طلب المنصة قد يستدعي عدة نماذج وأدوات؛ لا يساوي طلب مزود واحد.
- القيمة قابلة للتعديل إداريًا داخل المشروع المحدد، دون تحرير دالة أو نشر الواجهة. قيود 1..1000000، والإجمالي لا يقل عن حد الاتصال، وصف واحد فقط. لا يستطيع العميل إرسال allowance أو تغيير الصف، ولا يستطيع service_role الخاص بتنفيذ الطلبات تحديث الإعداد.
- RLS مفعل، لا وصول anon/authenticated، و service_role يقرأ الإعداد فقط. RPCv3 يقرأه داخل الحجز المتسلسل بدل الثوابت 5/100. إذا تعذر الإعداد تفشل العملية مغلقة قبل استدعاء النموذج.
- v2 يحافظ على schema القديم بحذف metadata الجديدة، و wrapper UUID ما زال يعمل. النشر السابق يستفيد من رفع الميزانية أثناء rollout دون استبدال بياناته. منع طلب آخر reserved/running محفوظ؛ المتابعة بعد اكتمال الرد فورية، دون مهلة 30 ثانية أو سقف 5 طلبات/دقيقة.
- GET الجاهزية يعيد قيم التطبيق الفعلية الموثوقة. تعرضها الواجهة AR/EN قبل الإرسال. رفض 429 يحمل limit/window/retry، وتعرض الواجهة الحد الحالي من الخادم بدل نص 5 ثابت أو رقم cached قديم. الألوان والصور والقالب محفوظة.
- الاتصال مرتبط بعنوان خروج موثوق مخزن HMAC، وليس حساب مستخدم مسجل؛ عناوين الشبكات المشتركة تشترك في سقف الاتصال. ربط باقات تطبيق فعلية يحتاج الهوية والمؤسسات المخططة؛ لا يدعي هذا التعديل إنشاء فوترة أو عضوية مدفوعة.

## إدارة الميزانية

المالك أو مسؤول DB فقط، داخل SQL Editor للمشروع `ruereqpvykwnakcnmxha`، يمكنه تعديل الصف القائم بعد اختيار ميزانية مناسبة:

```sql
update public.agentnexos_demo_limits
set connection_daily_limit = 1000, global_daily_limit = 10000
where singleton = true;
```

هذه القيم هي المنشورة في هذه الدفعة. لا قيم أسرار أو مفاتيح مطلوبة لتعديل الصف من لوحة المشروع. تغييرها لا يمسح عدادات الطلبات؛ يحتسب نافذة 24h المتحركة الحالية. لا cache لهذا الإعداد؛ الطلبات التالية تقرأه والواجهة تعيد قراءته عبر فحص الاتصال أو تحديث الصفحة.

## التحقق

اختبار SQL الحقيقي داخل transaction: تعديل fixture مؤقت إلى 7؛ قبول الطلب السادس والسابع فور اكتمال السابق؛ رفضالثامن مع limit7؛ رفض المتزامن؛ رفض الحد الإجمالي؛ توافق schema v2؛ منع service_role UPDATE و anon SELECT/EXECUTE. التغييرات والبيانات أُعيدت كلها بـ ROLLBACK، ثم ثبت الصف 1000/10000. لم يُمسح تاريخ أو رصيد المالك.

36 اختبارًا، typecheck/i18n/lint (0 أخطاء،18 تحذيرًا سابقًا)، build --webpack. اختبار UI mocked باللغتين يقرأ 1000 من الجاهزية ويعرض 37 من 429 لا 5 أو القيمة القديمة؛ يحفظ سياق الرسالتين ويستعيد نص المحاولة. الفحص الشامل ومعاينة Vercel والإنتاج والردود الحية تُوثق كل على حدة بأدلتها بعد اكتمالها. لا تجاوز حماية GitHub ولا حاجة لاشتراك Actions مدفوع.

هجرة `20261001015833_configurable_demo_budget.sql` مطابقة لسجل التطبيق الفعلي في Supabase؛ لا تطبيق مهاجرات المؤسسة القديمة. التراجع عن كود API/UI يبقى متوافقًا مع wrappers؛ يمكن إعادة قيم الإعداد إداريًا دون إسقاط الجدول أو فقد البيانات. المرجع السابق [FIX-FOLLOWUP](FIX-FOLLOWUP-2026-10-01.md) تاريخي فيما يتعلق بسقف 5.

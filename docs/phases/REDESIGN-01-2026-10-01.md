# REDESIGN-01 — public design and workspace identity

Owner authorized a new matte-black/green design, professional bilingual copy, public marketing pages, and authenticated agent access. Historical template components remain unrendered for reference.

## Identity and database

Supabase email registration requires confirmation (`email_autoconfirm=false`). Sign-in, registration, callback, cookie refresh and sign-out use the Supabase SSR client. The workspace validates the user server-side; the agent POST requires a confirmed authenticated user before reserving budget or invoking the model. Public pages and the project-brief download remain open.

Migration `20261001080819_workspace_identity.sql` was applied to authorized project `ruereqpvykwnakcnmxha`. Profiles have explicit authenticated grants and own-user read/insert/update RLS. No role is derived from user metadata. The SQL evidence uses transactional fixtures, rolls back all test data, and passed own-user read/update and cross-user read/update/insert denial. Security advisor returned only the two pre-existing intentionally server-only quota tables with RLS and no client policy; no profile finding.

Required runtime names: `NEXT_PUBLIC_SUPABASE_URL` (existing server URL fallback supported), `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` or existing `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Values must remain in deployment configuration. Never use a secret/service-role key for SSR authentication. Email delivery and allowed callback URLs must be configured in Supabase; confirmation is never bypassed.

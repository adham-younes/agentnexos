# Agentnexos — خطة الترقية الشاملة والتنفيذ المتتابع

تاريخ البدء: 2026-09-30 UTC. المرجع: طلب المالك الأخير يشمل **التطبيق كله**، ويحافظ على القالب والصور والألوان، ويصرح بمراحل متتابعة مؤتمتة تنتهي كل منها بدفع Git وPreview ثم Production موثق. هذه الخطة تتجاوز قيد «مرحلة واحدة لكل طلب» في الملفات التاريخية، وتحافظ على ضوابط الصلاحيات والأمان والأمانة.

## الدليل قبل الخطة

- خط أساس المصدر: `e856f3eb8d46f6c0fce76352b842bc02cb5f5c23`، وليس أرقام الحالة القديمة داخل الوثائق.
- فحص الشجرة بمحلل TypeScript وقراءة ملفات المنتج والمحتوى والمحرك والـAPI والأمان والتنقل: 143 ملف كود/إعداد و15,937 سطرًا في جرد الدفعة، مع جرد منفصل للوثائق والمهارات. جرد آلي للملفات لا يعني تدقيق أمان مستقل لكل سطر.
- مراجعة تعليمات AGENTS والخطة الرئيسية والحمايات والإصلاحات ودفعة UPGRADE-03؛ الوثائق القديمة تدعي تشغيلًا مؤسسيًا لا يثبته الكود الحالي.
- اختبارات البداية: typecheck و8 اختبارات SDK/API نجحت. فحص 30 حالة صفحة/لغة/عرض قبل توسيع المحتوى: HTTP 200، لا صور مكسورة أو تجاوز عرض أو pageerror.
- الإنتاج الحالي: GET `/api/agentnexos` يرجع `ready:false, code:DATABASE_UNAVAILABLE`. لا استدعاء Groq حي مثبت في هذه الجلسة. تقارير المصدر السابقة توثق رفض مفتاح الخادم بـ401.
- مشاكل مثبتة: لوحة ألوان فاتحة محلية في مساحة الوكيل، إرسال رغم غياب الجاهزية، سياق غير محدود في العميل مقابل حد 12 رسالة في الخادم، اختيار فريق حسب طول التاريخ، أدوات لا تعيد التحقق عند استدعائها مباشرة، فجوات في خطط الأعمال، نص إنجليزي «No supervision required»، «ابدأ مشروعًا» دون رحلة إعداد طلب، رابط About يرجع للأعلى، قائمة الهاتف لا تضبط التركيز، وضع تقليل الحركة غير مغطى، ملفات Runtime قديمة تعرض بيانات وإيصالات ثابتة كحقائق.

## بحث حي من مصادر أولية

## المراحل المؤسسية التالية وحدود الاعتماد

هذه أجزاء من الخطة الشاملة، وليست قدرات منشورة بمجرد كتابة مخطط أو اجتياز اختبارات محلية:

1. **الهوية والتفويض:** اختيار بيئة Agentnexos المحددة فقط، Auth موثوق، مؤسسات وعضويات، RLS، جلستان ومؤسستان حقيقيتان واختبارات منع التداخل. لا `tenant_id` يختاره العميل كمصدر صلاحية.
2. **التنفيذ الدائم:** event store محمي، state/version، stable operation IDs، idempotency، مهلات وإلغاء واستئناف، crash recovery/reconciliation. قائمة metadata داخل حقل `stages` قابلة للتحديث وليست سجلًا غير قابل للتعديل أو محرك replay.
3. **العزل والأداة الأولى:** موصل مصرح يختاره المالك، صلاحيات ضيقة، approval payload binding/expiry، إثبات الأثر، تعافٍ مجرب. Sandbox منفصل للملفات والشبكة والموارد والاعتماد إن لزم تنفيذ كود. لا إعادة فتح runtime القديم أو تعديل قاعدة إنتاجية بمخططات تاريخية.
4. **الذاكرة وMCP والتقييم:** ذاكرة ذات مصدر/trust/scope/TTL/evidence، النموذج يقترح والنظام يراجع ويثبت؛ اكتشاف أدوات عند الحاجة، MCP خلف policy gate؛ A2A عند وجود خدمة وكلاء مستقلة فعلية فقط. dataset عربي/إنجليزي وtrace grading وتكلفة/زمن ومقارنة مزودين على تشغيل حي.
5. **إطلاق مؤسسي محدود:** عملية ومالك وبيانات ونظام نهائي ومقياس خط أساس، shadow ثم assisted ثم capability-bounded autonomy. اعتماد تعهدات الدعم والتكلفة والخصوصية والدومين حسب عقد حقيقي.

**العوائق الحالية:** مفتاح خادم Supabase في Vercel Production غير صالح حسب الدليل المتاح؛ لا أسرار في هذا workspace. لا قناة تجارية موثقة ولا أول موصل مؤسسة معتمد. لا نطلب قيمة مفتاح في المحادثة ولا نسحب أسرار Vercel محليًا. توثيق GitHub السابق يشير إلى عائق فوترة Actions؛ يعاد فحص الحالة الفعلية لكل PR، ولا bypass/admin override.

## قواعد النشر والتراجع

- branch → اختبارات محلية → push → PR → Preview READY ومراجعة الرحلات → merge عادي إلى main → Production READY مطابق لSHA → فحص جميع المسارات والرحلة المتغيرة → تقرير.
- لا دمج إذا بوابة مطلوبة تمنعه؛ لا تعديل حماية الفرع أو إعدادات الفوترة.
- لا نجاح وهمي عند فشل مزود أو قاعدة بيانات. لا external writes ضمن التجربة العامة.
- التراجع بإعادة نشر نسخة سليمة أو revert محدد من خلال PR؛ لا reset destructive ولا مسح عمل المالك.
- حفظ الصور والأصول والخطوط وترتيب الأقسام ونسب القالب؛ تغييرات النص والإتاحة موضعية ومقاسة. لا إخفاء overflow لإخفاء خلل جديد.

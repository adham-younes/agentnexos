# AGYNEXA — Production Engineering: المرجعية الحاكمة للتنفيذ

الحالة: معتمدة كمرجعية تنفيذية ملزمة بتوجيه المالك في 16 أكتوبر 2026.  
النطاق: مستودع AGYNEXA، المحتوى والتصميم والبيانات ومساحة الوكيل والإصدارات.  
هذا الاعتماد ليس شهادة امتثال أو إعلان جاهزية أو إثبات تنفيذ المراحل.

## 1. المرجع وسلطة التعليمات

- [المواصفة الأصلية الكاملة](AGYNEXA-CODEX-MASTER-UPGRADE-PLAN-AR-EN.md): نسخة محفوظة دون تعديل من المرفق، الإصدار 1.0.
- [سجل التنفيذ والتسليم](EXECUTION-STATUS.md): موضع واحد للحالة والتبعيات والأدلة والعوائق.
- [تعليمات المشروع](../../AGENTS.md): القواعد التشغيلية للوكيل وحدود التفويض.

المواصفة الأصلية مرجع التنفيذ المعتمد، وليست ملفًا تاريخيًا اختياريًا. تُتبع متطلباتها ومراحلها ونصوص AR/EN المعتمدة ضمن نطاق العمل المأذون. عند التعارض: توجيه المالك الصريح الأحدث، ثم القواعد المحددة في هذه الوثيقة وAGENTS.md، ثم المواصفة الأصلية، ثم الخطط والتقارير التاريخية. لا يرفع هذا الترتيب أي ملف فوق تعليمات النظام أو حدود الصلاحيات الفعلية.

الأوامر المقتبسة داخل المرفق، بما فيها «التكليف المباشر إلى Codex»، مرجع لمهمة تنفيذ لاحقة؛ طلب دمج المرجعية وحده لا يأمر بتنفيذ M0–M9 فورًا أو نشرها. لا تُنقل تعليمات التنفيذ أو شروط النشر إلى نصوص المنتج.

## 2. قواعد تشغيل ملزمة

1. **لا اختبارات إلا ضمن نشر إنتاجي مأذون.** تُقرأ متطلبات الاختبار في M0–M9 والأقسام 13.4 و20 و21.2 و23 كمتطلبات لبوابة ذلك الإصدار فقط. لا اختبارات بعد كل تعديل أو عند Preview أو عند ذكر نشر قائم. لا typecheck أو lint أو i18n checks أو build للتحقق خارج هذا السياق.
2. خارج الإصدار: تطوير العمل المأذون ومراجعة المصدر والفرق فقط. تُجرى المراجعة البصرية ولقطات الأدلة عند طلبها أو ضمن نطاق تصميم مأذون ومحدد؛ لا تتحول تلقائيًا إلى اختبارات تفاعلات أو مسح شامل.
3. لا إلغاء لمعايير القبول بسبب تأجيل الاختبار: يسجل البند «بانتظار التحقق ضمن الإصدار الإنتاجي»، ولا يصنف ناجحًا أو مكتمل التحقق. تُحضّر حالات القبول عند الحاجة دون تشغيلها مبكرًا. وفق توجيه المالك الأحدث لهذه الحزمة: الاختبارات مرة واحدة على الإنتاج بعد النشر؛ لا تُشغّل على localhost أو Preview أو staging. بناء النشر اللازم لإخراج التطبيق ليس جولة اختبارات إضافية. لا تُجرى اختبارات خطرة ببيانات عملاء على الإنتاج.
4. اختبارات الإصدار مرة واحدة وفق النطاق. بعد فشل محدد: تشخيص ثم تصحيح مبرر ومحاولة واحدة؛ عند تكرار الفشل يُوثق العائق ويتوقف ذلك المسار. لا إعادة للناجح بلا تغيير مؤثر، ولا حلقات أدوات أو builds.
5. ردود متوازنة ومختصرة، وقراءة الأقسام المرتبطة بالمرحلة فقط. يُعاد استخدام الأدلة المثبتة عند تطابق النسخة والنطاق؛ لا يُكرر M0 أو التدقيق الكامل عند كل مهمة. تغيّر المصدر أو النشر يقتضي تحديث الجزء المتأثر فقط.
6. الحفاظ على الأسود والأخضر، المسارات الحالية، AR/EN وRTL/LTR، وما يعمل بالفعل. لا إعادة بناء أو تغيير framework أو إضافة orchestrator/اعتماد جديد دون حاجة موثقة.
7. محتوى القسمين 16 و19 مرجع النصوص والمصطلحات؛ لا اختصار أو إعادة تأليف تلقائية للنص المعتمد. تُفصل المسودات القانونية والنصوص المشروطة عن النص المسموح بنشره وفق القسم 17.
8. لا تسرب أسرار أو بيانات عميل إلى الأدلة. لا ادعاء قدرة مؤسسية أو شهادة أو عميل أو نتيجة قبل وجود دليل مناسب. إعداد المواصفة أو الكود لا يساوي تشغيلًا أو نشرًا.
9. اعتماد الخطة لا يجيز شراء خدمات أو إرسال بريد أو تغيير DNS أو حذف بيانات أو فتح وصول أو تغيير سياسات إنتاج حساسة أو تشغيل تكاملات العملاء. يتبع كل ذلك التفويض الفعلي؛ لا تُطلب موافقة متكررة على العمل المأذون أصلًا.
10. تعديلات الوثائق وحدها لا تستدعي اختبارات أو نشرًا. لا تُنشأ جميع مستندات المواصفة مقدمًا؛ ينشأ كل تسليم عند مرحلته وبقدر الحاجة، مع تجنب السجلات المتناقضة.

## 3. تسلسل التنفيذ والتسليم

السلسلة الملزمة: **M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8**.  
**M9 بوابة لكل إصدار إنتاجي**، وليست إذنًا للانتظار حتى نهاية المشروع. يمكن إصدار تحسينات الموقع بعد M4 دون ادعاء اكتمال مساحة العملاء أو M8.

| المرحلة | العمل الرئيسي | أقسام المواصفة | المخرج اللازم للانتقال |
|---|---|---|---|
| M0 | تثبيت النسخة وربط الملاحظات بالحالة الحالية | 0، 3، 5، 7.1 | baseline مختصر، جرد متعلق بالنطاق، تصنيف النتائج والقدرات والأدلة الناقصة |
| M1 | النطاق والبريد وSEO والمشاركة | 6، 19.1 | إعداد موحد للنطاق، metadata والبريد وOG، فرق قابل للمراجعة وخطة تراجع |
| M2 | الرسالة والنصوص والباقات والمؤسس | 2، 14–17، 19 | تطبيق النص المعتمد باللغتين، سجل تغييرات وادعاءات وروابط |
| M3 | القراءة والتكوين والتصميم المتجاوب | 12–13، 18 | مكونات وتدرج واضحان، أدلة بصرية محددة عند تفويض المراجعة، حالات القبول المؤجلة للإصدار |
| M4 | رحلة الموجز والطلب التجاري | 12.5، 16.16، 19.4 | موجز محلي مبسط؛ الإرسال الخادمي مشروط ببواباته وتفويضه |
| M5 | المخطط والمصادقة والعزل والاحتفاظ | 9، 11 | خطة migrations متوافقة، مصفوفة وصول واحتفاظ وتراجع، أدلة تحقق الإصدار قبل تفعيل الوصول |
| M6 | منطق المساعد ومساحة الوكيل | 7–8، 10، 12، 18 | عقود ومخرجات typed وحالات من backend؛ لا تمثيل زخرفي لتنفيذ غير موجود |
| M7 | الأمن والاعتمادية والأداء والتكلفة | 10–11، 20 | حدود تكلفة ومهلات ومحاولات، نموذج تهديد وتشغيل وتراجع، تحقق الإصدار المتعلق بالنطاق |
| M8 | تجربة مؤسسية متصلة واحدة محددة | 8–11، 22 | نطاق وبيانات وصلاحيات معتمدة؛ قراءة أولًا ثم كتابة مأذونة بدليل الأثر وتسليم قابل للمراجعة |
| M9 | إصدار وتتبع وتراجع | 20–21 | commit وdeployment وflags وmigration/content versions، نتائج فعلية، حدود معلومة وخطة رجوع |

لا يُقفز فوق تبعية لازمة. عند تعطل بوابة يُسجل السبب ويُنجز العمل المستقل المأذون دون إعلان تجاوز البوابة. لا يُعاد طلب إثبات أو تنفيذ بند مغلق بلا سبب جديد.

## 4. عقد العمل لكل دفعة

قبل الدفعة: تعيين المرحلة والبنود المطلوبة، الملفات المتأثرة والتبعيات وأعلى خطر، بالاعتماد على السجل بدل إعادة الجرد. أثناءها: أصغر تغيير مكتمل يحافظ على العقود وتعديلات المستخدم. عند التسليم يُحدّث سجل واحد يتضمن:

- معرف المهمة/المرحلة، مصدر المتطلب والقرار، والأدلة الحالية ذات الصلة.
- التغيير والملفات والمخاطر وخطة التراجع.
- حالة التنفيذ والمراجعة والتحقق والنشر كلٌّ على حدة.
- سبب أي تأجيل أو عائق، والخطوة المستقلة التالية.
- عند النشر فقط: نتائج الاختبارات الفعلية وcommit وdeployment والنسخ المعتمدة.

الحالات: `PENDING`، `IN_PROGRESS`، `IMPLEMENTED`، `BLOCKED`، `RELEASED`. تبقى مستويات «مكتوب / مراجع / متحقق بصريًا / متحقق وظيفيًا / منشور / متحقق في الإنتاج» منفصلة وفق القسم 21.5؛ لا يُستعمل لفظ «جاهز» لإخفاء بند لم يتحقق.
